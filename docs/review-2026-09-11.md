# Code review: 2026-09-11

The review covered Go forwarding, shared CLI / macOS connections, device lifecycles, Android API compatibility, the iOS listener, and build configuration. The maintainer had already verified usability; physical-device and end-to-end tests were not repeated, as requested.

## Fixed

- **P1: Cancellation did not unblock reads.** `RunConfig` could wait indefinitely for bytes during the handshake or an established connection, preventing pause, shutdown, or timeout cleanup from finishing. Cancellation now closes the stream throughout its lifecycle, and handshake waiting is bounded. Regression cases for both phases failed before the fix and passed afterward.
- **P1: Concurrent closure and ownership of usbmux descriptors.** The original implementation directly closed descriptors managed by Go, while closure and I/O modified fields concurrently. This could cause a reused descriptor to be closed again. The Darwin blocking-syscall compatibility path is retained, with synchronized closure that wakes blocked I/O and lets the original `net.Conn` release its own descriptor. Linux uses standard network connections. Regression tests cover concurrent closure, unblocking reads, and the original connection's closed state.
- **P1: The iOS listener did not restrict peers.** The listener bound to all interfaces and immediately replaced the current client on acceptance. It now checks for a loopback or local interface address, excluding other LAN hosts. This change passed iOS compilation but was not retested on a physical device.
- **P2: Old connection cleanup could affect a reattached device.** Cleanup waits for each device's old loop to finish before handling reattachment. Filtering by serial also handles usbmux detach events that contain only an ID. Shutdown waits for forwarding loops to release their resources.
- **P2: Status synchronization connections remained open.** The hub closes all client connections so viewers can detect disconnection. Ownership is released only after the hub stops, and viewer cancellation callbacks are cleaned up.
- **P2: Control operations lacked cancellation and timeouts.** ADB control I/O closes with its context, and name lookup, forward, and killforward operations have time limits. Cancellation also closes streams used by lockdown queries. TCP / UDP upstream connections close when the tunnel ends.
- **P2: Reconnection and multiple devices could corrupt PCAP files.** Each connection wrote another file header, and record locks were independent across connections. The relay now shares one Capture and serializes complete records. Concurrent record validation was added.
- **P2: DNS TCP length headers could arrive in fragments.** The two-byte length header is now read with `io.ReadFull`, preventing an incomplete length from being used after a short read.
- **P2: Transfer rates could underflow after reconnection.** Replacing a statistics object resets the delta baseline, and counter rollback is checked. A regression test was added.
- **P2: Android 5.x API incompatibility.** Two unguarded calls to the API 23 `getSystemService(Class)` overload were replaced with compatible calls. The false-positive VPN `systemExempted` lint error is suppressed only on the service, with the [official VPN exemption](https://developer.android.com/develop/background-work/services/fgs/service-types#system-exempted) documented in the manifest. No alarm permissions were added.
- **P2: Android failure paths left the UI stuck.** VPN establishment and listener failures are caught, handshake writes are covered by connection error handling, and a stopped state is published to clear the UI's preparing state. Heartbeats use a fixed delay to avoid replaying accumulated tasks after returning from the background.
- **P2: Stale iOS IPC callbacks could replay across connections.** Callbacks check the client generation. Manual stop also shuts down the container app's relay.
- Updated the README's installation steps, actual iOS forwarding path, shared-process behavior, and current limitations, and marked the original design document as historical.

## Follow-up items

- **P2: Device watchers do not reconnect after failure.** When `adb.Watch` or `usbmux.Watch` ends, `relay.Run` does not automatically recreate the watcher. Restarting the desktop process restores it, as documented in the README. A follow-up could add watcher retries with backoff and device-state cleanup.
- **P2: Persistence of iOS on-demand settings after manual stop.** `TunnelPreferences.prepare()` enables on-demand, while `stop()` only stops the current VPN and relay without persisting an on-demand disable. The system may later restart the extension. A follow-up needs to define whether manual stop also disables automatic connection, and serialize asynchronous preference saves with subsequent starts.
- **P2: Rapid Android stop / start within one Service instance.** Worker threads still share the `running`, TUN, and socket fields. If VPN binding keeps the instance alive, old-thread cleanup may interleave with a new session. A follow-up should isolate resources per session and wait for old threads to exit.
- The iOS relay still writes through a blocking socket. If the local proxy stops reading, it may occupy the serial queue indefinitely. A follow-up could add a bounded send queue and write timeouts.

These follow-up items were not validated on physical devices during this review. Passing compilation or unit tests does not mean they have been resolved.

## Validation

- Go: race tests across all packages and `go vet`.
- Desktop: CLI and macOS app builds, local ad-hoc signature verification, and a Linux amd64 CLI cross-build.
- Android: `assembleDebug` and `lintDebug`. Non-blocking warnings about SDK / dependency versions, icons, layouts, and translations remain.
- iOS: compilation for a generic iOS device target with `CODE_SIGNING_ALLOWED=NO`. This does not cover device signing, installation, or runtime acceptance.
